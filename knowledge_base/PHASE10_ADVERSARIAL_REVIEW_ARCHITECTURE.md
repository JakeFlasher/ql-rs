# Phase 10 adversarial architecture / SOTA review (v0.2.0)

Scope: cross-crate workflows, portfolio/XVA, benchmark integrity, terminal delivery, docs/release hygiene, and gaps versus production open-source quant stacks. This is a static review of the current tree (no code changes).

## Executive verdict

The workspace is an impressive research/teaching monorepo, but the advertised “production/SOTA” architecture is not yet an operable risk platform. Contracts are mostly ad-hoc Rust structs, valuation context is not propagated end-to-end, and portfolio/XVA paths silently bake in model, calibration and collateral assumptions. Benchmarks are generated by a custom timer and compare hand-picked implementations rather than independent, reproducible baselines. Terminal output is a demo renderer, not an interactive workstation. Release metadata and governance are insufficient for external users.

## Cross-crate architecture findings

* There is no canonical `MarketData`, `PricingContext`, `FixingStore`, `CalendarRegistry`, or `Currency/Unit` type spanning crates. Each crate accepts primitive `f64`, vectors and local specs; this allows inconsistent day-counts, calendars, discounting and currencies when composing (for example ql-portfolio builds Act/365 annual 1/2/5Y pillars while instruments support richer conventions).
* The umbrella `ql_terminal::prelude` glob-reexports every crate (`crates/ql-terminal/src/lib.rs`), causing ambiguous names and making semver/API ownership unclear. A downstream binary cannot depend on a small stable facade; all 23 crates become part of the public surface.
* Error handling is not compositional: `build_curve_system` calls `expect("curve calibration")`; portfolio duplicate IDs and XVA cube bounds use `assert!`. Invalid market data therefore aborts the process instead of returning a typed diagnostic suitable for a service.
* Generic `Real`/AD support is uneven. Several allocation and Black–Litterman routines convert to `f64` (`val()`) and solve with nalgebra, dropping derivatives and preventing SIMD/AD end-to-end risk. This contradicts the “one numerical kernel” claim.
* No schema/versioning exists for serialized trades, market snapshots, calendars, model parameters or benchmark fixtures. `serde` is optional per crate and no migration policy is documented.

## Portfolio / incremental DAG

* `PortfolioDag` caches in a mutable `HashMap<usize, ...>` keyed only by caller-provided numeric ID. IDs are asserted unique per call but removed trades are never evicted; stale cache entries can persist indefinitely and memory grows in long-lived services.
* Dependency hashes are hand-maintained (`trade_dependency_hash` in `ql-portfolio/src/dag.rs`). New trade fields or market dependencies can be omitted silently; there is no typed dependency graph or invalidation test for each field. Hashing raw `f64::to_bits` makes `-0.0`, NaN payloads and platform differences observable.
* Curve cache key omits any calendar, instrument convention, interpolation/extrapolation policy or curve configuration. Two snapshots with identical quote arrays but changed conventions reuse the same curve.
* `value_trade` reconstructs discount/forward curves from `params[..3]` and `params[3..]` and uses simplistic annual periods. Heston option rates are approximated as a flat continuously compounded rate from one discount factor; volatility, dividends/borrow and spot are not represented in the curve dependency. This is not a complete multi-curve/equity pricing context.
* Parallel valuation uses Rayon but writes aggregate counters and cache entries serially afterwards; no deterministic ordering guarantee is documented. The object is not `Send + Sync`, preventing concurrent requests without external locking.
* Risk output only has total NPV, par DV01 vector and equity delta. No trade-level provenance, quote IDs, scenario definitions, PnL explain, Greeks by factor, currency conversion, or audit trail is retained.

## XVA / exposure implementation

* `NpvCube` is a flat `Vec<T>` with runtime `assert!` bounds; no dimensions/units metadata, netting-set legal terms, currencies or valuation timestamps are attached. A cube can be combined with an incompatible curve silently.
* `simulate_hw1f_exposure_cube` uses one Hull–White factor and a single synthetic `NettingSetSwap` type. Real portfolios (options, FX, collateralized netting, initial margin, close-out) cannot flow through this API without bespoke code.
* CSA collateralization is a threshold/MTA clamp only. Margin period of risk, margin frequency, independent amounts, collateral remuneration, collateral currency, VM/IM segregation and rehypothecation are absent.
* CVA/DVA/FVA in `compute_xva` use constant hazard/loss/funding scalars and simple exponential survival. No calibrated hazard curves, wrong-way risk, stochastic rates, default dependence, close-out convention, settlement lag or collateral discounting. `epe` is an unweighted arithmetic mean over time points, not a time-integrated EPE.
* Exposure aggregation nets all netting sets before positive-part (`sum(ns)`), so legal netting-set boundaries are ignored. PFE quantile is rounded empirical order statistic; confidence, interpolation and sample error are not reported. `pfe_95` is hard-coded in the report type.
* AD values are preserved in EE/CVA but PFE is forced to `f64`; there is no XVA sensitivity/adjoint API and no regression tests against an independent engine.
* SIMM/DIM/MVA APIs (called from terminal/benchmarks) have no public model/version metadata or ISDA parameter-set identifier; production users cannot prove which SIMM release was applied.

## Benchmark integrity and reproducibility

* `ql-benches` implements a bespoke `Instant` timer (`harness.rs`) with one warmup, 31 samples and configurable loop repetition. It lacks CPU pinning, turbo/frequency control, allocation counters, confidence intervals, Criterion-compatible JSON, or machine/toolchain metadata.
* Baselines are hand-written alternatives in the same process (`suites.rs`), not pinned versions of QuantLib/other independent libraries. Several comparisons change algorithm and workload simultaneously (e.g., virtual-dispatch scalar loops vs. SoA SIMD, bump-and-rebootstrap vs. IFT), so “speedup” is not an apples-to-apples implementation result.
* The benchmark binary writes `BENCHMARK_RESULTS.md` and `knowledge_base/08_BENCHMARK_RESULTS.md` as a side effect of execution. Running tests or CI can dirty the checkout; no immutable fixture or signed result is kept.
* Parity checks compare only the final scalar returned by each closure (`last` sample). Randomized/RQMC workloads do not report confidence intervals or seeds in the result table; tolerances are often absolute and not scale-aware. A benchmark can pass while intermediate paths/Greeks diverge.
* README embeds 20 timing numbers as if release facts, but no hardware, compiler flags, commit hash, statistical protocol, or baseline source is recorded. Numbers are therefore not independently auditable.

## Terminal / delivery

* `ql-terminal` is a dependency-free ANSI/Braille renderer and `main.rs` drives fixed scenarios for a fixed number of frames. There is no input/event loop, terminal resize handling, key bindings, mouse support, alternate output formats (JSON/CSV), or graceful non-TTY detection. `--frames` sleeps 50 ms and emits escape sequences even when stdout is redirected.
* Snapshot mode renders four hard-coded scenarios and does not expose market-data or portfolio inputs. It is a demo, not a workstation users can connect to or automate.
* ANSI true-colour output and Unicode Braille have no capability negotiation; Windows/limited terminals and accessibility/screen-reader workflows are unsupported. Rendering allocates `String`s per frame and recomputes all analytics synchronously, so latency/back-pressure are unbounded.
* The prelude reexports `ql_benches`, making benchmark code a runtime SDK dependency and coupling release users to internal harness APIs.

## Documentation / release / modern open-source gaps

* `CHANGELOG.md` has a v0.2.0 headline, but it is a feature list rather than an API/behavioral migration record: it omits breaking-change annotations, deprecation/removal notes, upgrade examples, and per-crate compatibility. There is also no release checklist, MSRV policy, supported-platform matrix, reproducible lockfile policy, or crates.io publication status for the 23 packages.
* CI instructions in README require nightly fmt/clippy but no repository workflow, coverage, sanitizers, fuzzing, property tests, mutation tests, or differential tests are present. Financial edge cases (calendar boundaries, negative rates, NaNs, extrapolation, defaulted names) are largely assertion-driven.
* Missing production capabilities compared with QuantLib/OpenGamma/Strata and modern Rust finance projects include: holiday/calendar registry with timezone and fixing sources; instrument identifiers and legal documents; business-event/lifecycle processing; quote bootstrapping diagnostics and monotonicity checks; model governance and calibration reports; deterministic parallel RNG streams with audit metadata; persistent scenario cubes; REST/Arrow/Parquet adapters; observability/metrics; and plugin/version compatibility contracts.
* Numerical algorithms generally lack explicit domain checks (Feller/positivity, arbitrage bounds, PSD covariance, monotonic discount factors) and return unconstrained `f64`; users can obtain plausible numbers from invalid inputs without warnings.

## Prioritized remediation

1. Introduce a typed, versioned `PricingContext` (market snapshot, conventions, calendars, currencies, fixings, model IDs) and make every valuation accept it; replace `assert!/expect` with structured errors.
2. Redesign portfolio dependencies as typed factor IDs with deterministic cache eviction, provenance and serialization; add trade-level risk/scenario outputs and concurrency-safe immutable snapshots.
3. Split XVA into legal netting sets and collateral schedules; support calibrated hazard/discount/funding curves, MPOR, IM/VM and time-integrated EPE, with independent regression fixtures.
4. Replace custom benchmarks with Criterion/iai-perf plus pinned external baselines, machine metadata, deterministic seeds, confidence intervals and CI performance gates; keep generated reports outside source trees.
5. Treat terminal as a thin UI over a service API: non-TTY-safe plain/JSON output, resize/input handling, bounded frame scheduling and no benchmark crate in the prelude.
6. Publish release/MSRV/compatibility policy, API docs, model assumptions and validation datasets; add fuzz/property/differential tests and supply-chain/security scanning.

## Evidence and additional release blockers (independent spot-check)

The following observations were confirmed by source inspection rather than inferred from README claims:

| Area | Evidence | Operational consequence |
|---|---|---|
| Workspace API boundary | `ql-terminal/src/lib.rs` prelude glob-reexports the workspace, including `ql-benches`; the terminal package therefore couples application users to every crate and to benchmark internals. | A minor internal crate change can become a downstream compile break; package ownership and semver boundaries are unclear. |
| Error contract | `ql-portfolio/src/dag.rs::build_curve_system` uses `.expect("curve calibration")`; duplicate IDs and `ql-xva/src/cube.rs` indexing use `assert!`. | Malformed market/trade requests panic a server process; callers cannot classify recoverable input errors. |
| Cache lifecycle | `PortfolioDag.cache` is keyed by numeric trade ID and only inserts dirty trades; no sweep removes IDs absent from a later portfolio. | Long-lived risk services leak stale valuations and memory, and an ID reuse can expose an old entry if validation evolves. |
| Benchmark provenance | `ql-benches/src/harness.rs` reports median/IQR from `Instant`, but emits no CPU/toolchain/commit/allocator metadata and parity checks only the final sample value. | Published speedups are not reproducible or statistically comparable across hosts and can hide path-dependent divergence. |
| CLI safety | `ql-terminal/src/main.rs` enters alternate screen and writes ANSI control sequences whenever `--frames` is used, without TTY detection or signal-aware cleanup. | Piped logs/CI can be polluted; abnormal termination can leave a user's terminal in hidden-cursor/alternate-screen state. |
| Release automation | No `.github/workflows` tree is present; `rust-toolchain.toml` selects a toolchain but no MSRV or matrix is declared. | Formatting, tests, docs, package publication, security audit and benchmark regression checks are not enforced by a shared CI gate. |

These are P0/P1 release blockers for a service-facing 0.2.0 claim, even if numerical unit tests pass. A documented research release should explicitly downgrade the claim and publish the assumptions/limitations above.

These public projects reinforce the gaps above: typed market/product contexts,
modular calculation runners, stable release/compatibility policies, documented
error contracts and independent validation fixtures are expected in a
production-facing quantitative stack.
